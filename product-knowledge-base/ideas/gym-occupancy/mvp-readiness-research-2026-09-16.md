## 结论与任务边界

**PM 建议：APPROVED——可以进入正式 PRD / Checkpoint 编制，并在指挥者接受基线、确定唯一工程路径后开发“人工维护的忙闲信息＋真实会员绑定＋可维护课表”MVP。门店试点与公开发布尚未就绪，不计为通过。**

关键变化是：首版不依赖可靠出场事件。由获授权馆方人员现场观察并发布忙闲等级，会员看到来源和观察时间；超过有效期即降级。首页人工模式以状态词为主，不显示捏造的在场数字。自动门禁统计、人数估算和历史预测延后，明确的数据模型保留未来接入空间，但首版不建设通用数据平台。

这是一条完整可开发的业务路径，不是只有模拟首页：真实持久化、服务端角色权限、人工发布、会员核验、课表维护、失败反馈、记录撤销和审计均属于 P0。缺少门店资料不妨碍开发这些能力；缺少真实馆方更新、真实会员核验与正式课表，则不能称为真实门店 MVP 已投入使用。

本轮具体支持四项决策：无出场数据如何提供可信忙闲信息；会员入口何时算真正可用；课表展示与维护最小闭环；工程、开发工具、真机、试点分别怎样验收。只补充这些证据，不重复竞品/UI盘点、不修改源码、不外联馆方、不发布。完成报告和证据并回报指挥者后停止，不自行派单。

【授权口径】9月10日研究只允许研究投入属于当时状态；本轮合同明确用户授权指挥者推进 MVP 取舍、PRD / Checkpoint 和后续开发。这一后续授权支持常规方案继续推进，不需要重复询问。V0保留为“本店需求尚未通过真实使用验证”的证据标签，不作为否定最新授权的理由。本报告不自动更改其他产品WIP或把其他项目配置带入本项目。

## 1. 忙闲信息：选择人工主方案

| 方案 | 真正需要什么 | 能诚实展示什么 | 优点／成本 | 本轮取舍 |
| --- | --- | --- | --- | --- |
| 馆方人工现场观察 | 有观察权限的当班人员、覆盖观察的约定、可操作维护端 | “馆方现场观察：较空／适中／较忙；观察于 HH:mm” | 不接门禁也能用；持续人工成本，忙时可能最容易漏更 | **P0主方案**，有过期降级和审计 |
| 门禁已有在场人数API | 经现场校验的接口、覆盖通道、初始人数和漏报修正 | 有来源／时间的在场人数；映射拥挤等级仍须本店校准 | 自动化低日常人工；接入、准确性与供应商依赖未知 | 后续；不是本轮开发前置 |
| 自行统计进出事件 | 有效入场及出场事件、去重、乱序和修正 | 校验后的在场人数 | 维护复杂；仅“开门感应”不等于有效出场人数 | 后续；缺出场则不采用 |
| 仅入场＋停留时长模型 | 足够代表本店的停留分布、误差验证 | “估计在场约X～Y人”，附方法／时间／局限 | 可估计但目前无本店样本，固定两小时扣减无依据 | 暂缓，不用模拟模型补数 |
| 保持现状／前台询问 | 原有课表和前台 | 联系方式及前台口头答复 | 没有新维护系统成本；不便随时自助 | 对照及数据失效后的明确备用路径 |

### 人工发布闭环（产品方案）

1. 当班人员用本人业务账号进入维护端；服务端检查该门店的 operator 权限。不能靠隐藏按钮保护写入。
2. 现场观察力量区、有氧区及常排队器械的实际等待。首店试点前确定至少3个观察点和一页判断说明；不存在分区实时数据，因此会员端只呈现全馆人工结论。
3. 选择较空／适中／较忙，并确认“刚完成现场观察”。服务端记录 observation ID、门店、操作者、等级、`observedAt`、`publishedAt`、`validUntil`、revision。首版只允许当下提交，不提供任意回填旧观察时间的入口。
4. 写入事务提交成功后才显示发布成功；请求有幂等键、并发版本检查，失败不能将未提交值显示给会员。修正／撤销保留旧记录，操作者不能靠重新打开旧记录来刷新观察时间。
5. 会员请求最新有效观察；服务端按观察时间判定状态。修改课表、改文案、轮询、读缓存、应用重启都不能重置观察年龄。

建议观察标准：较空＝观察点基本无需等待；适中＝部分点需要轮换或短等；较忙＝多处持续等待、训练明显受影响。这是**本店待校准的操作定义**，不是行业容量或安全标准。课程中人数增多但力量器械不忙时，不自动判“较忙”；不同区域分歧明显、工作人员未巡视或无法判断时，选择“暂无法判断”，不能凭想象选较空。人工等级仅代表观察时刻，不保证会员到达时仍相同。

**默认有效期15分钟，`serverNow >= validUntil`即过期；建议10分钟一轮观察，变化明显时补更。** 两个数均为试点假设，不是来源事实。10分钟频率意味着每小时约6次操作，需实测观察加录入时间；值班时段无人承担更新时不承诺持续覆盖。维护端提示剩余有效时间，可主动标记“暂停更新”；不依赖后台定位或自动通知。

### 数据状态与文案：质量、来源、联网状态分开

| 情况 | 会员端必须表达 | 禁止行为 |
| --- | --- | --- |
| 人工观察仍在有效期 | “馆方现场观察 · 较空／适中／较忙 · HH:mm观察”；提示仅供到店安排参考 | 叫“准确实时人数”、无依据展示大数字或容量百分比 |
| 后续人工点数／模型估计 | 显式“人工点数”或“估计”及区间／方法／时间；仅已校验后启用 | 把区间中点变成确定人数；本轮默认不启用这两种数值模式 |
| 过期 | 主位置“忙闲信息已过期”；次级可显示“上次观察 HH:mm：较空（已过期）”，去掉新鲜状态强调 | 主卡继续绿灯“较空”；延长TTL掩盖缺乏更新 |
| 无记录、记录撤销、暂停更新、无效或未来时间戳 | “暂无法提供忙闲信息”，按原因显示未更新／暂停；提供已核实的联系入口（未配置则不编造号码） | 将空值、报错、未知当作0人或较空 |
| 网络失败／离线 | 明确连接失败；缓存值仅列作“上次获取的记录”，保留原观察时间并按可知年龄降级 | `wx.request success`就认定业务成功；把本机缓存当新数据 |
| 模拟 | 开发／演示环境醒目标“模拟数据”，与门店环境隔离 | 生产／试点数据写入接口接受simulation记录或fallback到fixtures |
| 闭馆 | 独立展示已配置的营业状态；忙闲可显示不适用 | 将闭馆等同“0人”，或未经核实默认零点清空 |

客户端首次打开／回到前台取新快照，前台默认60秒刷新并可手动刷新，离开前台停止轮询；状态在15分钟边界由本地计时及时降级，即使尚未到下一轮轮询。以服务端返回的`serverNow`与`validUntil`为准，持续会话用单调经过时间推进；应用重启离线／无法建立可信时间时不显示新鲜状态。本机改时钟不能延长有效期。后台网络不能假设持续可用，微信官方对后台请求有限制。[网络文档](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html)

### 人数需求与本轮取舍的关系

此前用户认可“预计人数大数字”的方向；当前可靠人数源缺失。本次提出的**变更建议**是人工模式用大状态词替代大数字，保留来源和时间。指挥者可按本轮授权采纳；若坚持首版必须有自动在场数字，则应对该数字子范围给REVISE／PAUSE，不能把累计入场或随机值包装为完成。忙闲方案本身无需等门禁自动化。

## 2. 必需会员入口：从入口到可用服务

仅有“我的／登录”按钮、假会员卡、客户端切换“已绑定”不满足完整MVP。最小有用服务为：**微信业务登录→馆方核验绑定→查看本店会员状态、核验时间及确有来源的有效期→遇到信息不符可请求前台处理→本人解除关联／删除小程序账户。** 不做二维码开门、续费收款或访问原始人脸库。

### 三种身份必须区分

| 层次 | 如何建立 | 能证明什么 |
| --- | --- | --- |
| 微信小程序用户 | 用户选择登录，`wx.login`→本应用服务端→code2Session，服务端签发可撤销业务会话 | 该AppID下的微信身份，不证明姓名、手机号或健身房会员资格 |
| 本店会员 | 馆方人员在原系统核对现有会员凭据，再把会员内部引用绑定到当前已登录用户 | 馆方在核验时确认的会员关系；后续有效／到期／撤销需维护 |
| 馆方操作员 | 系统负责人按独立名单配置服务端角色及门店范围 | 能维护指定门店；普通会员不能自授角色，会员绑定不会自动授予operator |

官方依据：[登录流程](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/login.html)、[code2Session](https://developers.weixin.qq.com/miniprogram/dev/server/API/user-login/api_code2session)。**OpenID不是匿名数据，也不是自然人实名证明；UnionID不作为首版必要条件。** 不从客户端接收任意openid当作登录成功，不将AppSecret、session_key或微信access_token发给客户端，不在日志保存临时code或业务令牌。网络/限流/无效code时清楚报错，重新登录获取新code，不能重放旧code或回退假登录。

**operator初始化与撤销的候选规则**：工程环境由维护者在服务端预配置独立测试operator；真实环境由项目负责人确认馆方授权人员后，将其已核验业务userId加入单店服务端角色名单。首版不开发通用角色管理后台，也不提供客户端自助升级。授予／撤销记录执行人、对象、门店、时间和原因，日志不带完整令牌。每次管理请求重检当前服务端角色；移除角色后旧会话立即不能写入，不缓存旧operator权限继续放行。测试与真实角色名单隔离；CP4须有真实负责人确认名单的记录。

### 推荐绑定：前台核验当前用户的待绑定请求

【设计建议】不依赖馆方API或微信手机号接口。用户登录后发起待绑定请求，显示短时配对码；前台当面核对其原会员卡／原系统允许的身份凭据，将本店内部会员引用和当前请求关联。**代码只是找到当前小程序账号的手段，实体会员资格由馆方核验，不能让任意持码者自动成为会员。**

- 待绑定请求绑定服务器会话与门店；建议8位随机数字配对码，10分钟到期、一次使用；每账号最多1个活跃请求，重建使旧码失效。8位／10分钟为设计默认值，PRD可明确实现细节。
- 只有operator能检索请求；前台与用户当面比对同一配对信息，确认正在处理的账号。按账号与操作者限制错误查询（建议每10分钟最多5次），不开放匿名枚举会员接口。
- 同一门店一个会员引用默认绑定一个小程序账号；已绑定／并发绑定时拒绝自动覆盖，转人工解除后重核验。提交绑定、消耗请求和写审计在同一事务完成。
- 馆方填写状态与原系统有效期；“无固定到期日”须显式确认，不能用空值表示无限有效。未取得有效期但原系统显示有效时，标“馆方已核验，具体有效期待确认”，不显示永久会员。核验记录显示`verifiedAt`；有效期未定的记录不授予未来会员专属权益。
- 有确定到期时刻的资格由服务器自动过期；人工撤销立即改变服务端授权。已打开的客户端最迟下次刷新更新（默认60秒）；敏感操作每次服务器重检，不等页面刷新。换手机／清缓存后，重新微信登录仍得到同一已绑定关系。
- 原系统没有API时，需要馆方在取消、续费、转卡时维护本系统；所以本系统显示“馆方核验记录”，不是替代门禁或原系统的实时权益账本。首版不据此自动开门、扣费或放行。
- 本人解除绑定需有效会话和明确操作；立即终止本账号的会员关联，前台重新核验才能绑定；删除小程序账户同时撤销会话、清除个人业务缓存并按约定清理关联，不代表注销原健身房会员合同。保留审计的字段和期限在PRD说明，不保留凭证原图／人脸。

这种方案需要**现场授权人员和一次真实会员核验**才能证明业务身份可用。没有馆方人员时可以在独立测试租户用测试operator和合成会员验证流程，但验收记“工程绑定流程通过”，不能记“真实会员核验通过”。

### 会员有限状态与授权口径（候选基线）

业务登录、绑定关系、会员资格分别存储；以下为服务端合成的页面状态，不能由客户端选择。公共信息对所有状态可读；已登录用户只读自己的最小状态，不因“有效”获得operator权限。首版会员服务是查看／维护自身关联，不以此自动开门或授予原馆权益。

| 状态 | 触发与可操作项 | 授权限制 |
| --- | --- | --- |
| 未登录 | 无有效会话；可主动登录 | 不返回个人会员信息 |
| 未绑定／已解绑 | 没有当前关联／本人已解除；可重新发起请求 | 不显示有效会员，不沿用旧会员资格 |
| 待核验 | 请求有效但尚未完成馆方核验；可取消／到期后重建 | 配对码不授予会员权限 |
| 已核验但有效期待确认 | 馆方确认关系但没有明确期限或无固定期限依据 | 显示核验时间与待确认；不授予未来会员专属权益 |
| 有效 | 馆方确认有效，期限未到或明确无固定到期日 | 仅本人状态服务；所有后续权益若扩展须另写服务端规则 |
| 过期 | 服务端当前时间达到确定到期时刻 | 不按有效会员授权；续费由馆方核验更新，不靠用户勾选 |
| 已撤销 | 馆方撤销关系／资格 | 撤销优先于旧有效期；敏感接口立即失效，不能凭旧页面恢复 |
| 已删除账户 | 本人删除业务账户 | 撤销业务会话与关联，客户端回公共未登录态；重新登录创建新业务账户时不自动恢复旧绑定 |

撤销优先于旧资格，解绑／删除去掉当前关联；过期按服务器时间判定。历史状态只作受限审计，不作为恢复权限的依据。PRD保持这些可观察规则，字段命名可由dev实现设计确定。

### 微信隐私与手机号边界

【事实】[手机号快速验证官方页](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/getPhoneNumber.html)写明用户点击同意、主体资格要求，并且“快速验证”不保证实时验证；手机号code与登录code不同，不能混用。这是可选后续绑定途径，不解决手机号与本店会员记录匹配错误、号码变更或转卡问题。首版不调用该能力，也不以是否拥有此接口为开发门槛；不在此轮购买调用额度。

【事实】[隐私协议开发指南](https://developers.weixin.qq.com/miniprogram/dev/framework/user-privacy/PrivacyAuthorize.html)要求先在后台声明所处理信息，已声明的隐私接口还需同步用户同意；`getPrivacySetting`、`openPrivacyContract`及相关同意流程存在基础库版本边界。未声明、拒绝和接口不支持必须处理；微信官方弹窗不替开发者决定业务用途、会员身份或所有后端数据处理规则。[填写说明](https://developers.weixin.qq.com/miniprogram/dev/framework/user-privacy/)

【方案】公共忙闲和公共课表不强制登录；用户进入会员服务时说明处理OpenID关联、本店会员引用、核验状态／时间／有效期的用途。后端也属于数据处理范围，不能因为不用手机号／位置就勾选“未采集隐私”。首版不主动收集姓名、手机号、头像、定位、运动健康、人脸及原始会员凭证；必要的会员引用和微信身份只在服务端关联。用户拒绝登录／隐私相关操作后仍可看公共信息，不能反复弹窗。页面可查看隐私说明，存在相关接口时按官方授权流程调用；版本不支持则降级公共浏览并明确说明会员功能暂不可用，不默许绕过。

首版无定位、推送、相机扫描需求，配对码可手工录入；这减少能力和权限依赖。需要后续扫码时再新增相应权限说明及验收。建议观察业务记录保留30天、操作审计90天，会员数据在有效关联期间保留并提供删除处理；这些是待PRD细化的工程默认假设，不是法定期限或已对外承诺。实际运营主体、隐私指引、联系渠道及平台类目资格须在真实用户阶段核实。

## 3. 课表：能够维护，也能够诚实为空

【推荐P0】“今日／本周”列表＋一行当前排课摘要；每节课至少有稳定ID、课程名、门店时区、开始／结束时间、状态（scheduled/cancelled）、修订号和更新时间。教练名、容量、剩余名额均非必填；没有这些数据不虚构。取消保留带取消标记的记录，改期更新同一课程并保留变更记录；跨日时段按时间区间重叠查询，不只按开始日期归组。

维护端支持新建草稿、编辑、取消、批量确认某日期范围“课表已核对并发布”。发布对象是课程集合和覆盖日期范围的一个版本，空课表必须由operator明确确认后才表示该范围无排课；没有发布覆盖时显示“课表尚未发布”。保存草稿不会影响会员端，发布原子完成；两人编辑时发生版本冲突就要求刷新，不覆盖对方新数据。

| 场景 | 展示与维护规则 |
| --- | --- |
| 未取得任何实际课表 | 开发维护能力及空态；真实环境没有预置课程。工程环境可用标记合成样本，不记作真实课表 |
| 某天已确认发布、课程数为0 | “该日无排课”，并显示覆盖范围／更新时间；不称实际空闲或自由入场 |
| 当前时段有scheduled课程 | “按课表：XX课 HH:mm–HH:mm”；结束不等于所有人离开；半开区间 start≤now<end |
| 课程取消／改期 | 重新发布后读取新版本；取消有明确标记，改期显示现行时间和更新提示；本期不承诺自动通知 |
| 跨午夜／跨周 | 按门店时区和区间查询，课程仍在进行时不因周一切换消失；夏令时地区需后续按真实地点确认 |
| 发布范围已结束、当天不在覆盖范围或撤回发布 | “该日期课表尚未发布／已撤回”，不循环复用上周表；不能把数据库空结果自动当无课 |
| 离线或刷新失败 | 显示缓存版本及“未能确认最新变更”；新请求成功后才清除提示，不说已同步 |

按周课表在所声明的覆盖日期内有效，不套用忙闲15分钟有效期。维护人应在改期／取消时发布变更；客户端首次／回前台和前台60秒刷新。后台临时关闭排课展示时显示不可用。真实试点前至少取得一个完整周的馆方核定课表（也允许馆方明确核定全周无课）；每节课时间有效，冲突提示并由馆方确认，不能凭场馆约150平方米推算名额。

## 4. 推荐完整 MVP 与数据边界

会员端三步主路径：**打开场馆页→看来源／时间与忙闲、今日课程→需要个人服务时进入“我的”查看或绑定会员。** 中文、两个主入口、少量卡片，视觉沿用已认可的留白方向；具体颜色不阻塞PRD。

| 优先级 | 必须交付的可用能力 | 明确完成边界 |
| --- | --- | --- |
| P0 | 场馆忙闲展示、自动过期／不可用／离线态、营业与联系信息 | 使用真实服务端数据，数据源可人工；没有数据时诚实为空 |
| P0 | 微信业务登录、前台配对核验绑定、本人会员状态／有效期口径、撤销／解除／删除流程 | 服务器关联持久化，账号隔离；不是客户端假卡 |
| P0 | 今日／本周课表、发布覆盖范围、取消改期及失败态 | 与维护端使用同一正式数据源，不独立维护一份示例JSON |
| P0 | 馆方维护端：现场观察发布／撤销、课表草稿发布、会员核验／撤销、最近操作记录 | 经server-side operator鉴权；建议同一小程序内独立管理页面，角色不放入公共会员导航 |
| P0 | 服务端持久化、租户／角色检查、时间口径、幂等／版本冲突、操作审计、环境隔离 | 重启和多客户端访问保持一致；合成测试数据不能进门店环境 |
| P1后续 | 自动门禁／在场数字、模型估计、历史忙闲、器械目录与报修、个人到店历史 | 本轮不实现，补数据或需求后另派单 |
| 暂缓 | 预约／候补／名额账本、支付续费、二维码开门、社交、AI教练、完整训练日志、营养／恢复、定位围栏、后台推送 | 不从竞品功能倒推首版必须有 |

建议使用原生微信小程序作为会员端和轻量维护端，服务端提供最小HTTPS接口及数据库；不引入竞品源码。具体语言、数据库、云托管或自建由指挥者与dev在CP0按现有可用环境选定，不因未知供应商而强行采购。官方说明自建请求需合法域名及证书，微信云托管特定调用方式可免配置通讯域名；本报告不假设已有任何云资源。[网络官方文档](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html)

### 有限试点：不无限等待，也不跳过真实结果

建议先安排一个7天、每天两个明确覆盖窗口（高峰与平峰）的试点；只承诺这些有值班人员的窗口。选5–8名自愿会员，现场观察人员按10分钟节奏更新，另一个人在窗口内随机抽查。门店正常营业但未覆盖时允许过期，不能假装全天实时。

试点候选判据（设计假设，非市场或行业标准）：至少30次独立抽查；覆盖窗口中有效观察覆盖率≥80%；“显示较空但观察点已持续明显排队”的误导事件≤10%；至少3位会员在不同日期主动查阅两次以上，并能说明信息如何帮助其到店安排；记录每次观察＋更新耗时和馆方是否愿意继续承担。有效覆盖率＝约定营业观察窗口内有未撤销且未过期记录的时长／窗口总时长；缺更、暂停和断档计入分母。误导率＝新鲜“较空”但独立现场判断明显排队的次数／所有抽查新鲜“较空”的次数，同时报告该分母；分母为0或不足10次时只记“证据不足”，不记0%或通过。重复查阅使用自愿参与者的访谈／观察记录，首版不为了实验默认接入跨用户行为追踪SDK。

小样本只用于决定下一轮，不证明普遍需求或付费。任何越权、真实会员错绑立即暂停相应功能并纠正；新鲜覆盖不足或误导超阈值时REVISE观察流程／状态解释，不直接延长TTL去凑分。馆方无法投入观察或无人愿意使用则PAUSE试点／重新判断产品价值。

不取得馆方合作不能完成CP4，但可先开发CP1/2并验证已定义的完整闭环；在等待外部条件时停止于真实可记录的交付层级，不循环增加无关调研、不自动扩大开发范围。
