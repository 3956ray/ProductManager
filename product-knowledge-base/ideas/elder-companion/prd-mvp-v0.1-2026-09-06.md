## 问题

用户打开网页后，需要迅速知道“可以找人陪老人聊天、散步、插花、下棋”，看到具体的人，判断合不合适并购买一次服务。首版要验证选择与交易，不以长申请表或访谈代替实际使用。

## 目标用户

老人本人和代订子女共用网页；首次浏览无需选角色。提交预约时才区分“自己使用／为家人预约”。运营用简易后台维护少量实际服务者；陪伴者初期可通过运营确认订单。

## 分发与价值捕获假设

微信及社交平台分享直达首页、活动筛选页或公开人选详情。首版按单购买；用户看见总价，平台服务费规则可配置，实际金额待确定。无默认会员费或自动续费。

## 创始人时间预算

单区域、有限可售时段和少量真实人选作为容量控制建议，数量随可管理供给确定；先不承诺全国服务。每单人工沟通和处理耗时必须记录，每周投入上限待 Product Lead 安排。

## 目标

完整跑通“浏览→选人→预约确认→付款→服务完成→评价／再约”。前端像可使用的服务平台，后台允许人工；不把“提交了意向表”计作成交。

## 非目标

原生 App、小程序专属开发、左右滑核心模式、算法推荐、实时站内聊天、多城市自动派单、服务者自助入驻、订阅套餐、社区团体活动售票暂不做。社区活动是可以陪同参加的内容，一对一关系保持不变。

## 方案

### 六个用户页面＋一个运营后台

| 页面 | 内容与交互 | 必须处理的状态 |
| --- | --- | --- |
| 首页／列表 | 短介绍、城市／区、活动筛选、单列人选卡；卡片含照片、介绍、方言、活动、区域、时长价格；详情与收藏入口 | 加载、失败重试、无匹配、未开通地区、无供给；不虚构人选 |
| 人选详情 | 授权照片、简介、可选自我介绍视频、服务内容、语言、区域、档期、价格、核验说明、评价；底部预约按钮 | 暂无评价、下架、暂无档期；视频可选，不阻塞浏览 |
| 预约确认 | 自己／家人、活动、时长、日期、地点、联系人、特别偏好；展示总价及取消说明 | 表单错误、重复提交、档期变化；详细地址到此才收集 |
| 订单详情／支付 | 状态、时间地点、服务者、双方确认进度、费用、支付、取消、退款、联系客服 | 未确认、待付款、付款中、已预约、退款处理中等 |
| 我的预约／收藏 | 通过验证后的联络方式找回订单；收藏保存候选，返回原筛选位置 | 空记录、失效登录、收藏人选下架；未登录本机收藏不承诺跨设备 |
| 完成与反馈 | 确认完成、老人／购买人分别反馈、投诉入口、再约这位 | 未完成不可评价、重复评价、原人选无档期 |
| 运营后台 | 人选与服务上下架、档期、预约确认、老人同意、通知、异常、退款、结算记录 | 操作权限、审计、冲突档期、失败待处理队列 |

首屏建议主标题“一对一老年陪伴”，支持文案“聊天、散步、插花、下棋，找位合拍的人一起做”。文案可迭代；大段服务说明放详情和帮助，首屏应看见活动入口及部分人选。

### 人选与服务展示规则

- 不先填申请表或登录才能浏览。活动筛选直接更新结果；筛选条件可分享，不包含隐私。
- 默认可服务区域匹配，其他排序依据使用明确的档期或价格；不伪造智能匹配分。
- “陪着插花”和“插花教学”分别表述；材料、场地、交通是否包含必须明确。
- 时长与价格成对出现；未确定价格的演示卡只能预览，不允许真实付款。
- 真实人选没有订单时显示“暂无平台评价”；照片、身份与核验标识必须有依据。
- 预约以服务为单位，一单一位老人、一位陪伴者、一个连续时段；额外人员需求转人工确认，不自动改变报价。

## 用户流程

1. 浏览与筛选；看详情，选择服务与时间。
2. 提交预约并验证购买人的联络方式；成功后返回有编号的订单。
3. 运营联系陪伴者确认档期；代订同时确认老人意愿，可用短链接或电话记录，无需老人建账号。
4. 双方确认后生成待付款订单并暂占档期，显示准确总价与付款截止时间。
5. 支付渠道确认成功后显示已预约，发送确认信息；仅前端跳回不能当作付款成功。
6. 到场和结束由服务者报告、运营留痕；用户可确认完成或提出异议。
7. 评价与再约。再约预填原人选、活动；重新确认档期、当前价格和用户意愿。

初期通知由运营通过已同意的联络方式发送，订单页是状态依据。网页不承诺自动推送或客服即时在线。

### 状态与交易规则

| 订单状态 | 进入条件 | 后续动作 |
| --- | --- | --- |
| 待确认 | 用户提交有效预约 | 陪伴者接单且服务对象同意→待付款；拒绝／超时→未成单；用户可取消 |
| 待付款 | 报价、同意与档期都确认 | 成功支付→已预约；超时→已过期并释放档期；用户可取消 |
| 已预约 | 服务端核实支付 | 到场→服务中；取消→按已确认规则处理退款 |
| 服务中 | 已预约且记录到场 | 结束→待完成确认；异常→人工处理并保留记录 |
| 待完成确认 | 服务者报告结束 | 用户确认或运营核实→已完成；异议→争议处理中 |
| 已完成 | 完成记录核实 | 允许评价、再约与后续投诉；结算单独管理 |
| 取消／未成单／过期 | 对应原因明确 | 终态；改约创建关联的新订单，不复活旧价格与付款 |

支付、退款、争议与服务订单分别记录。退款申请不代表退款成功；部分退款、全额退款和失败均有金额与渠道依据。争议中暂停结算。

待确认和待付款期限为必填运营参数，确定后在用户页面展示。收到过期订单的迟到支付通知，不恢复冲突订单，进入异常核查与退款队列。预约拒绝无需收费。

### 数据与权限

复用完整版的陪伴者、服务、档期、预约、支付、记录、评价对象。订单增加价格规则版本、同意时间／方式、状态变更日志与操作者。

公开：授权的人选资料、区域、服务、可售档期与发布评价。购买人：自己的订单与必要摘要。陪伴者：被确认分配的服务与必要联系信息。运营：按职能访问；所有敏感访问和订单修改留痕。

订单短链接不可仅凭顺序编号读取；访问前验证权限。同意链接使用不可猜、限时令牌，拒绝后立即停止流程。日志不记录身份证、完整手机号或私密谈话；具体留存期限上线前设置并告知。

## 验收标准

| 编号 | 可观察的通过条件 |
| --- | --- |
| A01 | 在 360、390、430px 手机及桌面可浏览和预约；无横向溢出、按钮遮挡；iOS Safari、Android Chrome、微信内置浏览器检查通过 |
| A02 | 选择“插花”仅显示提供该服务的人；返回列表保留筛选和滚动；空结果可重置 |
| A03 | 没有真实档期／价格的人选无法付款；未登录可看详情，提交时才验证联系人 |
| A04 | 同一表单连续点击只创建一单；两个订单竞争同一时段时最多一个进入有效占位 |
| A05 | 为家人预约未获同意时不能付款；拒绝、换人、改活动或改时段会触发相应重确认 |
| A06 | 支付中断可查回状态；重复回调只记一次；金额不符、过期支付进入人工队列 |
| A07 | 用户可查看取消理由、退款金额和进度；失败退款不会显示成功；后台能对账 |
| A08 | 未完成订单不可评价；无评价不显示虚构星级；子女反馈标明来自购买人 |
| A09 | 再约带入原服务者并重新查档期；没有档期时可换日期或自主换人 |
| A10 | 未授权访问其他人的订单、后台和联络资料被拒绝；分享详情不包含私人订单数据 |
| A11 | 客服可查到异常订单的责任人和处理状态；争议订单不自动结算 |

## 指标

| 指标 | 定义 |
| --- | --- |
| 人选兴趣 | 去重详情访问人数／去重列表访问人数；剔除员工与演示流量 |
| 预约转化 | 提交有效预约的去重购买人数／去重详情访问人数；分本人／代订、地区、活动、渠道 |
| 老人接受 | 明确同意的代订预约数／已取得老人明确答复的代订数；未答复单列 |
| 供给接受 | 接单数／发给服务者的有效邀请数；同时看响应时间与拒绝理由 |
| 付款转化 | 已付订单数／已发出有效待付款报价的订单数；重复支付不增单 |
| 履约完成 | 完成订单数／服务时间已经过去的已付订单数；取消仍计入分母并分类 |
| 同人复约 | 首单完成后 30 天内再次付款预约同一人的人数／已有完整 30 天观察窗的首次完成人数 |
| 退款与运营成本 | 退款金额／实付金额；另记录每单人工分钟数、服务者收入与实际成本 |

最小事件：列表查看、筛选、人选查看、预约提交、双方确认、付款成功、到场、完成、退款成功、再约提交。浏览事件采用最小化匿名记录，购买漏斗以服务端订单数据为准，不把健康信息放入统计。

首批真实数据用于建立基线，不预设未经依据的行业转化率。观察提交却无法确认、确认却不付款、完成却不复约分别发生在哪里。记录没买的可选原因，不强迫用户填写。

## 风险

冷启动无法接单：按真实区域与可售时段开放。资料不真实：运营核验再上架。老人和购买人预期冲突：分开确认与评价。陪伴者取消：提供改期、用户确认换人或退款。身体不适：停止活动、必要时急救并通知联系人；普通陪伴者不诊断。报价变更：付款前重确认，付款后不单方加价。

## 上线 / 灰度

1. 可点击原型：页面和流程齐备，用明确标记的演示人选与测试支付；验证使用体验，不声称成交。
2. 真实预约版：上线有限真实人选、档期、运营后台与联系人验证；支付暂不可用时明确为预约请求，不能算完整交易 MVP。
3. 完整交易 MVP：实际收款、退款、服务和复约闭环可用；先限制真实可履约区域与订单容量。

三个步骤是交付检查点，不重复设置访谈前置门槛，也不等同本轮已批准部署。发生交易异常可关闭新预约／支付，已有订单仍可查询、联系与退款。发布后以行为数据调整页面和服务内容。
