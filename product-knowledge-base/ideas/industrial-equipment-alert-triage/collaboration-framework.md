## 当前建议

使用三个系统，但每个系统只承担一种主职责：

- **飞书：人与业务流程的主入口**。用于群沟通、访谈纪要、需求池、PRD 审批、决策、待办提醒和验收确认。
- **GitHub：代码与技术变更的主入口**。用于源码、技术任务、数据契约、架构决策、Pull Request、自动测试和发布记录。
- **Codex 产品知识库：分析与综合判断的工作记忆**。用于读取原始输入、区分事实与假设、准备访谈、综合需求、生成 PRD 草稿和更新长期知识。

不要在三个系统同时维护同一份可编辑 PRD。飞书中的已批准 PRD 是业务范围的正式依据；GitHub 只保存带版本号的“研发实施基线”和技术说明；Codex 知识库保存分析摘要、来源链接、同步时间和待决策事项。

## 为什么需要 GitHub

Discovery 阶段只用飞书也能开始，但一旦进入原型或开发，就应建立独立的私有 GitHub 仓库，原因包括：

- 代码、配置、测试和数据结构需要版本控制。
- 每项研发工作需要与 Issue、分支、Pull Request 和验收结果关联。
- 技术方案变更需要可审查、可回滚的记录。
- Codex 可以在本地仓库中完成开发、校验和准备变更。

GitHub 不应成为学长和老板日常讨论需求的主要界面，也不应存放未经批准的真实设备数据、客户信息、密钥或生产访问凭证。

## 单一事实源规则

| 内容 | 正式主来源 | 其他系统如何引用 |
| --- | --- | --- |
| 群聊、会议安排、行动提醒 | 飞书 | Codex 只沉淀结论和来源；GitHub 不复制聊天 |
| 原始访谈纪要与附件 | 飞书 | Codex 保存摘要与飞书链接 |
| 需求池与状态 | 飞书多维表格 | GitHub Issue 回填需求 ID 和飞书链接 |
| 已批准业务 PRD | 飞书文档 | GitHub 保存带日期/版本的实施基线并链接原文 |
| 产品决策与审批 | 飞书决策记录 | Codex 知识库同步结论；GitHub 引用决策 ID |
| 源代码、测试、配置 | GitHub | 飞书引用 Issue、PR 和发布链接 |
| 技术架构与数据契约 | GitHub | 飞书 PRD 引用对应版本 |
| 研究综合、假设、跨来源分析 | Codex 产品知识库 | 结论经人确认后写回飞书 |
| 真实设备数据 | 经批准的数据环境 | 飞书/GitHub/Codex 只放脱敏样本、Schema 或链接 |

## 飞书空间结构

建议建立一个项目知识空间或文件夹，暂定名为“工业设备智能告警 MVP”，包含：

1. **项目首页**
   - 一句话目标
   - 当前阶段
   - 本周重点
   - 阻塞与待决策
   - 关键文档入口
2. **沟通与会议纪要**
   - 学长需求确认
   - 老板访谈
   - 现场工程师访谈
   - 周会与复盘
3. **需求池（多维表格）**
   - 所有需求、问题、证据、状态和 Owner
4. **PRD 与验收**
   - PRD 草稿
   - 已批准版本
   - 验收记录
5. **决策与风险**
   - MVP 范围决策
   - 数据与资安审批
   - 生产接入与安全边界
6. **数据请求与样本登记**
   - 数据类型、Owner、授权状态、脱敏状态、保存位置

飞书群只用于讨论和提醒，重要结论必须回到需求池、PRD 或决策记录，不能只留在聊天记录中。

## 飞书需求池字段

先使用一张多维表格，避免过早拆成复杂系统。

| 字段 | 说明 |
| --- | --- |
| Requirement ID | 例如 `REQ-001`，跨系统唯一编号 |
| 标题 | 一句话描述问题或需求 |
| 类型 | 用户问题、业务需求、数据需求、技术约束、风险、Bug |
| 来源 | 学长亲历、老板原话、工程师反馈、系统数据、团队假设 |
| 用户/角色 | 谁遇到问题 |
| 场景 | 在什么设备、站点和流程节点发生 |
| 问题与影响 | 发生了什么，造成何种损失 |
| 证据 | 访谈纪要、截图、数据样本或事件链接 |
| Confidence | 假设、低、中、高 |
| 状态 | 新输入、待澄清、已验证、待批准、已批准、Dev Ready、开发中、待验收、完成、暂不做 |
| Priority | 暂不排、P0、P1、P2、P3；优先级需 Product Lead 批准 |
| Owner | 下一步负责人 |
| Approver | 范围、数据或上线批准人 |
| Next action | 下一个具体动作 |
| PRD/Decision | 飞书文档链接 |
| GitHub Issue/PR | 进入开发后回填链接 |
| Updated at | 最近更新时间 |

## 飞书工作流

### 第一阶段：先手动运行

1. 学长在群里提供信息或参加访谈。
2. 访谈纪要进入飞书文档。
3. Product Lead/Codex 将独立问题提炼为需求池记录。
4. 学长确认事实是否准确。
5. Product Lead 决定是否“已验证”或“待批准”。
6. 只有状态进入 `Dev Ready`，才创建 GitHub Issue。
7. GitHub Issue 和 PR 链接回填飞书。
8. 开发完成后，飞书中由业务 Owner 做验收确认。

### 第二阶段：增加自动化

流程稳定后再配置：

- 新需求进入“待澄清”时通知 Owner。
- 缺少证据、Owner 或下一步时自动提醒。
- 需求变为 `Dev Ready` 时触发创建 GitHub Issue，或通知技术负责人创建。
- GitHub PR 合并后更新飞书为“待验收”。
- 验收完成后更新为“完成”，并记录版本与证据。

只做单向字段同步：飞书决定业务状态，GitHub决定技术状态。不要让两边同时修改同一个状态字段。

## PRD 流程

1. **Discovery Note**：Codex 根据访谈和证据形成问题分析，不视为已批准需求。
2. **PRD Draft**：在飞书形成可评论草稿，包含问题、用户、范围、非目标、数据、风险和验收标准。
3. **事实确认**：学长/现场工程师确认流程和设备事实。
4. **范围批准**：老板或 Product Lead 确认 MVP 场景、资源和边界。
5. **PRD v0.1 Approved**：锁定业务范围与验收条件。
6. **Implementation Baseline**：将已批准范围的版本快照写入 GitHub `docs/product/`，标注飞书原文、批准人、批准日期和版本。
7. **技术拆解**：通过 GitHub Issues 和里程碑拆成数据、后端、前端、模型、测试和部署任务。
8. **变更控制**：任何业务范围变更先回到飞书批准，再更新 GitHub 实施基线。

仓库规则：

- 默认私有。
- `main` 保持可运行，变更通过分支与 Pull Request 合并。
- 每个开发 Issue 必须包含飞书 `Requirement ID` 和 PRD 链接。
- 每个 PR 必须链接 Issue，说明测试结果和数据/安全影响。
- 真实生产数据、密钥、访问令牌、客户名称和未脱敏日志不得提交。
- 原型阶段只使用合成数据或经过 Owner 批准的脱敏样本。

## 第一周最小搭建

不需要一次做完全部集成。首轮只搭建：

1. 一个飞书项目群。
2. 一个飞书项目首页。
3. 一张需求池多维表格。
4. 一份学长访谈纪要模板。
5. 一份 PRD 草稿模板。
6. 一个本地 Git 仓库；确认权限后再创建私有 GitHub 远程仓库。
7. 手动使用 `Requirement ID` 和链接关联飞书与 GitHub。

先完成一次真实需求从“访谈 → 澄清 → 批准 → Issue → PR → 验收”的完整流转，再决定是否开发飞书机器人或双系统集成。
