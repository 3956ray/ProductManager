# 产品调研

以待做决策为起点，建立可核查的证据链，再形成建议。把公开网络研究视为真实用户研究和产品指标的补充，不把它们互相替代。

## 读取上下文

开始前依次读取：

1. `product-knowledge-base/BOARD.md`
2. 与研究对象相关的 idea、PRD、历史研究和决策记录
3. `product-knowledge-base/agents/agent-roster.yaml`
4. `product-knowledge-base/agents/operating-rules.md`

复用已有证据，不重复已经完成的搜索；发现冲突时保留双方来源。

## 选择研究路径

- 新市场或进入机会：市场格局、细分、替代方案、进入障碍、需求证据。
- 指定竞品：产品能力、定位、定价、用户反馈、商业与未来方向。
- 公开用户声音：评论、论坛、Reddit、X、社区中的问题语言和切换触发；输出仅作为待访谈验证的假设。
- 产品 discovery：问题强度、当前替代方式、历史行为、最便宜的验证实验。
- 决策备忘录：综合内部与外部证据，比较选项、风险和未知项。
- 定期刷新：只报告相对上次记录的实质变化，并指出哪些旧假设失效。

## 执行流程

### 1. 定义研究契约

先确定：

- 本次研究支持的具体决策。
- 目标用户、地区、时间范围和产品边界。
- 必须回答的问题与明确不做的范围。
- 交付物、截止时间和停止条件。

信息不足但风险低时，用标记为「假设」的合理前提继续；会显著改变范围或结论时再询问用户。

### 2. 建立搜索计划

给出简短计划，说明将检查哪些证据线、优先使用哪些来源、如何处理时效和矛盾。随后按 `references/source-policy.md` 执行。

至少覆盖两条相互独立的证据线。涉及市场规模、价格、法律、医疗、金融或重大 roadmap 方向时，必须包含权威一手来源。

### 2a. 按链接惰性调用短视频工具

默认不加载平台专用处理流程。扫描用户输入和待核查材料中的完整分享文案；只有发现具体作品链接，且研究问题需要读取该作品内容时，才调用 `video-downloader`：

- 抖音：`douyin.com`、`v.douyin.com`、`iesdouyin.com`
- 小红书：`xiaohongshu.com`、`xhslink.com`

按最小必要范围处理：只需标题、作者、发布时间或发布文案时使用 metadata-only；关键 claim 依赖口播时才下载并执行 ASR；依赖界面演示、实物表现或画面文字时，再检查视频画面。链接失效、内容私密、要求登录或无法合法取得时，记录为来源缺口，不绕过访问控制；可请用户提供本地视频、截图或文字稿。

只有平台名称、没有具体作品链接，或研究对象是平台市场、公司、政策与平台级竞品时，不调用 `video-downloader`。来源等级按作者身份和 claim 判断，不按平台统一判断；单条短视频只能形成线索或假设，不能单独证明市场需求、代表性、付费意愿或产品效果。

### 3. 收集证据

按证据线收集，不按网站堆砌材料：

- 权威线：政府、监管、统计、论文、标准、财报和正式披露。
- 产品线：官方产品页、定价页、更新日志、文档、应用商店和 GitHub。
- 用户线：真实访谈、客服、评论、论坛、Reddit、X 和社区讨论。
- 内部线：指标、Slack、Drive、会议记录、销售或研究资料。

每条重要材料立即转换为 Evidence Card；使用 `references/evidence-and-eval.md` 的字段，不把搜索摘要当作最终证据。

可将相互独立、只读的证据线交给 subagent 并行处理。每个 subagent 只返回 Evidence Cards、来源缺口和矛盾，不做最终优先级判断，不同时修改共享文档。

### 4. 独立核查

对会影响结论的 claim 执行以下检查：

1. 打开原始页面，而不是只读搜索片段或二手转述。
2. 检查发布日期、事件日期、地区、样本和口径。
3. 判断来源是否真正独立；同一新闻稿的多次转载只算一条证据线。
4. 寻找反例、负面证据和无法证实的部分。
5. 标记引用究竟支持整个 claim，还是只支持其中一部分。

高风险或结论冲突时，把 Evidence Cards 交给 `evidence_verifier_agent` 独立复核。

### 5. 综合为决策材料

始终分开呈现：

- 事实：来源直接支持、可检查。
- 推断：由已列证据推导，说明推理跳跃。
- 假设：为继续工作而采用、尚未验证。
- 证据缺口：没有找到或当前无法取得。

先给结论，再给关键证据、反证、选项权衡、建议实验和所需审批。不要用宏观市场数据直接推算订单、付费或留存；不要把 GitHub 热度、Reddit 投票或 X 讨论量当作需求验证。

### 6. 通过质量门

按 `references/evidence-and-eval.md` 评分。低于通过线、存在未核实关键数字、引用不支持 claim，或把推断写成事实时，不得给出高置信度的 GO 建议；应缩小结论、补充研究或建议验证实验。

### 7. 写回与维护

- 用户只要求分析或报告时，不自动修改知识库；给出建议写回位置。
- 用户要求更新、落地或已明确授权本地写回时，更新对应长期文档并保留历史来源。
- 已核验 Evidence Cards 需要进入长期知识时，交给 `knowledge-loop` 执行来源登记、串行写回、INDEX/LOG 更新和 Lint；不要在两个 skill 中复制来源政策。
- 所有新长期文档包含 Owner、Last updated、Source、Confidence、Related decisions、Next review date。
- 所有产品研究结论同时记录 Research Quality 与 Validation Level；研究质量达到 85 不代表需求、付款或留存获得验证。
- 影响 roadmap、定价、上线、法律/合规、客户承诺或外部系统的动作，先取得人类批准。
- 需要持续关注时，记录基线与下次复核日期；下一次只报告变化、失效假设和新增风险。

## 输出要求

使用中文，模型名、agent id、文件名和配置字段保留英文。每个重要事实就近附原始链接。默认输出「Just Enough」版本：只保留足以支持当前决策的证据、限制和下一步。
